# 3차시: 프로젝트 저장과 연구 기록

## 이번에 구현한 범위

- 프로젝트 입력값 검사, 저장 후 폼 초기화, 연결 오류와 테이블 누락 안내 구분
- 프로젝트별 실험 목적과 단계 편집, 준비물·장비·단위·조건·주의 사항 입력
- 단계 추가·삭제·순서 변경, 프로토콜 저장·조회
- 날짜·시간·종류·메모를 포함한 일정 추가·수정·삭제와 완료 처리
- 저장하지 않은 변경이 있을 때 화면 이동 및 새로고침 확인

## 코드 흐름

`app/page.tsx`는 프로젝트를 불러오고 새 프로젝트를 저장한다. 선택한 프로젝트의 ID를 `components/project-records.tsx`에 전달한다. 이 컴포넌트는 프로토콜과 일정을 해당 프로젝트 ID로 조회하며, 저장 요청이 성공한 뒤 화면의 저장 상태를 갱신한다.

`protocols`는 프로젝트마다 한 행을 사용한다. 실험 단계의 순서는 `steps` JSON 배열의 순서로 보존한다. `research_events`는 일정마다 한 행을 사용하며, `project_id`로 소속 연구를 구분한다. 날짜와 선택적인 시간을 별도 필드에 저장해 날짜만 있는 마감 일정도 표현한다.

`lib/supabase.ts`는 환경 변수로 클라이언트를 만든다. `lib/project.ts`는 공통 프로젝트 타입과 오류 안내를 제공한다. `supabase/schema.sql`은 테이블, 외래 키, 인덱스와 수업용 RLS 정책을 정의한다. 현재 정책은 사용자별 분리가 없는 수업용 정책이다.

## 원격 DB 연결 후 확인 순서

1. Supabase Dashboard에서 프로젝트가 활성 상태인지 확인한다. Project URL과 `.env.local`의 `NEXT_PUBLIC_SUPABASE_URL`이 일치하는지 확인한다.
2. SQL Editor에서 `supabase/schema.sql` 전체를 실행한다. 기존 프로젝트를 삭제하지 않고 테이블과 정책을 준비하는 SQL이다.
3. 개발 서버를 재시작하고 새 프로젝트를 만든다. 새로고침한 뒤 목록에 남는지 확인한다.
4. 프로젝트를 선택하고 프로토콜 목적과 단계를 입력한다. 저장 후 새로고침하여 값과 순서가 유지되는지 확인한다.
5. 연구 일정에서 일정을 추가하고 제목·날짜를 수정한다. 완료 상태를 바꾸고 새로고침한다. 삭제 후 다시 불러와 사라졌는지 확인한다.
6. 두 프로젝트에 서로 다른 기록을 저장하고 화면을 전환해 기록이 섞이지 않는지 확인한다.

## 이번 실행의 제한

타입 검사, 변경 파일 린트와 배포용 빌드를 통과했다. 테스트용 API 응답을 사용하는 브라우저 검증으로 프로토콜 편집·순서 변경·저장 실패 후 재시도, 일정 추가·수정·완료·삭제, 프로젝트 간 기록 분리, 저장 전 이동 확인과 PC·모바일 화면을 확인했다. 전체 저장소 린트는 기존 UI 컴포넌트의 오류로 통과하지 못했다.

현재 설정된 Supabase 호스트에 대한 조회 요청은 `ENOTFOUND`로 실패했다. 원격 테이블 생성과 실제 DB 저장·조회는 검증하지 못했다. 브라우저에서 쓰는 Publishable key로 SQL DDL을 실행할 수 없으므로 SQL Editor 실행이 필요하다. 실제 AI 응답과 통계 계산은 다음 개발 범위다.
